## 1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы выведите в мониторинг и почему?

```
Системные метрики
Цель: контролировать использование ресурсов, особенно ЦПУ.
•	CPU usage (load average или процент использования)
Причина: вычисления нагружают ЦПУ — это критичная метрика для раннего выявления проблем.
•	Memory usage
Причина: вычисления могут потреблять много памяти.
•	Disk usage (объем занятого пространства)
Причина: отчеты сохраняются на диск, переполнение диска приведет к сбоям.
•	Disk I/O (скорость чтения/записи)
Причина: если отчёты большие, возможна нагрузка на диск.

Метрики HTTP-сервиса
Цель: следить за доступностью платформы и поведением API.
•	Количество HTTP-запросов (requests per second)
Причина: позволяет понять загрузку сервиса и пиковые моменты.
•	HTTP response codes (доля 2xx / 4xx / 5xx)
Причина: рост 5xx — признак проблем на сервере, 4xx — возможно ошибки клиентов.
•	Среднее и 95-й перцентиль времени ответа (latency)
Причина: увеличение времени ответа может сигнализировать о деградации.

Метрики вычислений
Цель: оценить корректность и эффективность основной логики.
•	Количество завершённых вычислений (успешно и с ошибками)
Причина: падение количества или рост ошибок может говорить о внутренних проблемах.
•	Время выполнения вычислений
Причина: резкий рост может свидетельствовать о снижении производительности или перегрузке.
•	Очередь задач
Причина: рост очереди — сигнал, что система не справляется вовремя.
Метрики сохранения отчетов
Цель: гарантировать, что результаты сохраняются без потерь.
•	Ошибки записи отчётов на диск
Причина: критичная метрика, т.к. потеря результатов нарушает бизнес-логику.
•	Время сохранения отчета
Причина: чтобы выявить аномалии в I/O или задержки.

Такой набор покрывает:
•	мощность сервера (CPU, память, диск);
•	доступность и корректность API;
•	корректность и эффективность вычислений;
•	целостность хранения результатов.

```

## 2. Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы можете ему предложить?

```
Уровень успешных вычислений (SLO: success rate)
Метрика:
доля успешно завершённых вычислений / общее число вычислений

Почему:
Это показывает, насколько часто система выполняет свои обязанности перед клиентами. Например:

"99.5% вычислений завершаются успешно" — понятная метрика для менеджера.

Время отклика системы / Время выполнения задачи
Метрика:

Среднее / 95-й перцентиль времени отклика API

Время выполнения пользовательской задачи

Почему:
Отражает скорость обслуживания. Можно сказать:

"95% задач обрабатываются менее чем за 10 секунд"
Это уже качество сервиса.

Доля ошибок (Error Rate)
Метрика:
количество запросов с ошибками 5xx / общее количество запросов

Почему:
Говорит о стабильности сервиса. Можно отслеживать и сообщать, если error rate > 1% в течение 5 минут — это показатель деградации.

SLA-доступность платформы
Метрика:
время доступности сервиса / общее время

Почему:
Классическая метрика уровня SLA. Например:

"99.9% доступности за последние 30 дней"
— это конкретный бизнес-ориентированный показатель.

Количество успешно сохранённых и доставленных отчётов
Метрика:
успешно сохранённые отчёты / сгенерированные отчёты

Почему:
Показывает, насколько результат действительно доставлен клиенту, а не просто посчитан.

Количество обслуженных клиентов и их активность
Метрика:

Количество уникальных пользователей в день

Количество активных сессий / задач

Почему:
Дает понимание масштаба использования и успеха продукта у клиентов.

Как это визуализировать
Можно собрать дэшборд уровня продукта (например, в Grafana), в котором не будет слов "CPU", "inode", "RAM", а будут блоки вроде:

Успешные вычисления: 98.7%
Отчётов создано за сутки: 12,487
Среднее время обработки задачи: 8.2 сек
Ошибки сервиса: 0.3%
Доступность: 99.95%
Активные пользователи сегодня: 214

```

## 3. Вашей DevOps команде в этом году не выделили финансирование на построение системы сбора логов. Разработчики в свою очередь хотят видеть все ошибки, которые выдают их приложения. Какое решение вы можете предпринять в этой ситуации, чтобы разработчики получали ошибки приложения?

```
В условиях отсутствия финансирования на полноценную систему сбора логов (например, ELK, Loki, Splunk), нужно найти простой, дешевый и рабочий способ, чтобы разработчики могли получать ошибки приложений.
Вот реалистичный план действий с учётом ограничений:

Переиспользовать текущую систему мониторинга (например, Prometheus + Alertmanager)
Решение:
Настроить экспорт ошибок из приложений в метрики Prometheus через кастомные метрики.
Prometheus будет собирать эти метрики, а Alertmanager — присылать алерты при росте ошибок.
Преимущества:
Не требует отдельной системы логирования.

Разработчики сразу видят ошибки в Grafana/Prometheus.
Можно настраивать алерты на превышение порогов.

Логирование в stdout/stderr + systemd journal или файловую систему
Решение:
Разработчики пишут логи в stdout/stderr. Приложения запускаются через systemd, Docker или supervisord, которые уже умеют сохранять stdout.
Затем:
Настроить journalctl или ротацию логов в /var/log/app.log

Уведомления об ошибках через email/slack/webhook
Если приложение может само "репортить" ошибки:
Настроить отправку критичных ошибок (например, исключений) по email, в Slack или в Telegram-бота.
Простой webhook-сервер можно поднять даже на bash/Python.

Минимальная дешевая система логирования
Если чуть-чуть ресурсов всё же можно найти — используйте:
Efk (Elasticsearch + Fluentd + Kibana) — можно заменить Elasticsearch на более лёгкий бекенд.
Loki + Grafana — дешёвая и быстрая альтернатива ELK. Loki — очень лёгкий, можно запустить даже на одном сервере.
Но это — если будет "окно" в бюджете.

```

## 4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?

```

Вы рассчитываете SLA как:
SLA = сумма 2xx / сумма всех HTTP-запросов

2xx мало → SLA ≈ 70%
Нет 4xx и 5xx, то есть ошибок нет
Но SLA всё равно низкий.


Где может быть ошибка?
Если нет 4xx и 5xx, значит оставшиеся HTTP-коды — неуспешные, но и не считаются ошибками в классическом понимании. Какие это коды?

Вероятные "невидимые" коды:
1. HTTP 3xx (редиректы)
Не ошибки, но и не успешные ответы (в смысле вашего SLA)
Если ваш сервер часто отвечает 301/302 (например, при переадресации на /login) — они занижают SLA

2. HTTP 1xx (информационные коды)
Очень редки, но технически считаются не 2xx

3. HTTP 0 или отсутствие кода (timeout, сбои на клиенте)
Некоторые прокси, балансировщики или мониторинги могут логировать код 0 при обрыве соединения

4. Проблема в сборе метрик
Возможно, вы не собираете все 2xx, но при этом все запросы учитываются (например, через nginx вы собираете общее количество, но фильтр 2xx применён к подмножеству)

Что делать:
1. Добавьте в мониторинг детализацию по кодам
Вы сразу увидите, какие коды занимают 30% "провала" SLA

2. Проверьте, как вы собираете метрику
Иногда фильтры в экспортере или прокси неправильно агрегируют коды:
Пример ошибки: status =~ "2.*" — не учитывает 200, если формат строки другой (например, code="200 OK")
Или фильтр code =~ "2.." применяется только к frontend-инстансам, но не к backend

3. Обратите внимание на редиректы (3xx)
Они часто массово используются в аутентификации: например, все незалогиненные пользователи получают 302 на /login.

Вывод:
Ошибка — в том, что вы не учитываете коды 3xx, 0 или просто не все 2xx собираются.
Ваш SLA-счётчик "думает", что это неуспешные запросы, хотя они не классифицируются как ошибки (5xx, 4xx).

Как правильно:
Перепроверьте, что попадает в числитель (2xx)
Разделите http_requests_total по кодам (2xx, 3xx, 4xx, 5xx, 0)
Уточните SLA: может быть, SLA нужно считать по успешному "бизнес-результату", а не по 2xx

```

## 5. Опишите основные плюсы и минусы pull и push систем мониторинга.

```

Pull-модель мониторинга
Пример: Prometheus по умолчанию работает по pull-модели.

Плюсы:
Простота в безопасности (особенно внутри сети):
Только мониторинг-серверу нужен доступ к целям. Цели не должны знать, куда "пушить".

Контроль со стороны сервера:
Сервер точно знает, кого и когда опрашивает. Легко определить "мертвые" цели (если не отвечают на опрос).

Меньше зависимости от клиента:
Цель не должна беспокоиться о логике отправки данных, повторах и буферах.

Удобно для автодискавери:
Мониторинг может динамически находить новые цели (через сервис-дискавери или Kubernetes API).

Минусы:
Требуется доступ от сервера к каждой цели:
Сложно, если цели находятся за NAT, в облаках, в другом регионе или защищены (например, в private VPC).

Не подходит для событийных (разовых) данных:
Если приложение краткоживущее (batch job), оно может "умереть", до того как его опросят.

Сложность с метриками от краткоживущих контейнеров/функций:
Если контейнер запущен 3 секунды — Prometheus может не успеть его опросить.

Push-модель мониторинга
Пример: StatsD, Graphite, Prometheus PushGateway, Telegraf + InfluxDB

Плюсы:
Хорошо работает с краткоживущими задачами:
Например, скрипт может сам "запушить" метрику и завершиться.

Не требует доступа от мониторинг-сервера к целям:
Особенно удобно в сложных/изолированных сетевых условиях (например, на edge-устройствах, внутри мобильных сетей, за NAT и т.д.).

Просто масштабировать:
Клиенты пушат в промежуточные агрегаторы, которые масштабируются независимо.

Минусы:
Сложнее контролировать "живость" целей:
Сервер не знает, когда метрика перестала поступать из-за ошибки, а когда — потому что цель завершила работу.

Требуется буферизация и retry на клиенте:
Если сеть недоступна, клиент должен сам повторять попытки отправки, что усложняет реализацию.

Меньше прозрачности:
Сложно понять, кто именно пушит метрику (особенно если не настроена строгая идентификация).

Безопасность:
Требуется защищать endpoint, куда пушатся метрики (например, от спама, подмены или DDoS).

Что выбрать?
Pull — лучший выбор для статических, длительно работающих сервисов (web-приложения, базы, бекенды), особенно в Kubernetes.

Push — необходим для краткоживущих задач, batch-job'ов, или при невозможности доступа от сервера к целям.

```

## 6. Какие из ниже перечисленных систем относятся к push модели, а какие к pull? А может есть гибридные?

```

Разбор по системам:
1. Prometheus — Pull
Основная модель: Pull

Как работает: Prometheus сам опрашивает таргеты по HTTP (/metrics)

Push возможен? Да, через PushGateway, но это костыль для краткоживущих задач — не основная модель

Вывод: Pull-модель, с ограниченной поддержкой push через PushGateway → Гибридная (ограниченно)

2. TICK stack (Telegraf + InfluxDB + Chronograf + Kapacitor) — Push
Основная модель: Push

Как работает: Telegraf, агент на хосте, пушит метрики в InfluxDB

Push возможен? Да, это базовый принцип

Вывод: Push-модель

3. Zabbix — Гибридная
Zabbix Agent (активный) → Push (агент сам отправляет данные на сервер)

Zabbix Agent (пассивный) → Pull (сервер сам опрашивает агент)

Вывод: Гибридная система — поддерживает и push, и pull

4. VictoriaMetrics — Гибридная (в зависимости от источника)
Поддерживает прием push-метрик через:

Prometheus Remote Write

Influx Line Protocol

OpenTSDB protocol

Может использоваться в pull-стеке, если метрики приходит из Prometheus

Вывод: Гибридная, зависит от источника данных

5. Nagios — Pull
Основная модель: Pull — Nagios опрашивает проверяемые сервисы через плагины

Push возможен? Не по умолчанию, только через сторонние дополнения или кастомные скрипты

Вывод: Pull-модель

```
